GoMesh Architecture

An end-to-end encrypted messenger: a Go relay server, a Go client engine shared by a terminal client and a SwiftUI app for macOS and iOS, and a binary protocol over TLS 1.3. This page shows how the backend is built, how each kind of message moves, and the exact bytes on the wire.

Architecture

Three processes, one trust boundary

Clients run the whole cryptographic engine. The server is a relay that authenticates devices, orders group changes and stores ciphertext until it is acknowledged. Files bypass the relay and go to object storage under signed URLs.

Data flow

How a message moves

Each arrow is one packet, labelled with its type and size on the wire. Every packet is a 55-byte header plus a body; blue arrows carry an encrypted body.

Wire format

Packets, byte by byte

All integers are big-endian. Sizes marked n, P or m depend on content: a name, the plaintext, the number of members.

Scope

What this design does not claim

  • Not audited. It implements published designs (a signed-prekey handshake, a ratchet, sender keys) in my own code, tested with 300+ unit and end-to-end tests and 15 fuzz targets.
  • The directory is trusted until safety numbers are compared. The server hands out bundles, so a malicious server could substitute keys; the 60-digit safety number is the check.
  • Metadata is visible to the server: who talks to whom, when, and how much.
  • One account, one device. Signing in elsewhere moves the account.
  • The server sees the password at login (over TLS, stored as argon2id). OPAQUE would remove that.
  • Group removal costs about one direct message per pair of members, fine for hundreds, not thousands; MLS is the design for that scale.
